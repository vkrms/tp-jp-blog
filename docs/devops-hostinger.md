# Для devops: настройки хостинга jp-blog.travelpayouts.com (временный документ)

Дата: 2026-11-26. Удалить после того, как вопросы закрыты.

## Коротко

Сайт `https://jp-blog.travelpayouts.com/` — статический (HTML/CSS/JS, сборка Astro), выкладывается из GitHub Actions по SSH (rsync в `public_html`). Файл `.htaccess` в корне сайта есть и выкладывается, но **платформа его не применяет**: ни редиректы, ни своя страница 404, ни заголовки кэша не работают. Судя по структуре (`~/websites/<id>/public_html`, `/opt/h5g/...`, заголовок ответа `platform: hostinger`), это новая управляемая платформа Hostinger, а не классический shared-хостинг на Apache/LiteSpeed.

Нужны три настройки (или доступ, чтобы я выставил их сам). Ниже — что именно, зачем и как проверить.

## Что сейчас происходит (проверено 2026-11-26)

| Что настроено в `.htaccess` | Что на самом деле |
|---|---|
| HTML: `Cache-Control: public, max-age=0, must-revalidate` | HTML отдаётся с `cache-control: max-age=31536000` (год) |
| `ErrorDocument 404 /404.html` | любой несуществующий адрес отдаёт **200 и главную страницу** |
| `RedirectMatch 301 ^/en/articles/... /articles/.../en/` (3 правила) | старые адреса отдают 200 и главную, редиректа нет |
| `RewriteRule` http → https | работает (видимо, делает сама платформа) |
| `Options -Indexes` | 403 на листинг каталога (видимо, по умолчанию) |

Файлы в `public_html` при этом правильные: `.htaccess` на месте, старые каталоги удалены деплоем.

## Что нужно

### 1. Кэш HTML — самое важное

Статьи на сайте обновляются автоматически (агенты публикуют правки цифр, новые статьи). С кэшем HTML на год вернувшиеся читатели могут неделями видеть старые версии страниц.

Нужно:
- **`*.html` (и адреса каталогов, отдающие `index.html`)**: `Cache-Control: public, max-age=0, must-revalidate` (или короткий `max-age`, например 300).
- **`/_astro/*`** (файлы с хешем в имени): можно оставить `max-age=31536000, immutable` — так и задумано.
- Если перед сайтом CDN Hostinger: чтобы он уважал заголовки сервера **или** чтобы кэш сбрасывался при деплое (тогда нужен способ сбрасывать его из GitHub Actions — API-токен/команда).

### 2. Настоящая ошибка 404

Сейчас любой неизвестный адрес отвечает «200 + главная» (похоже на режим SPA-fallback). Для поисковиков это «мягкие 404» (Search Console их помечает), а битые ссылки становятся невидимыми.

Нужно: неизвестный путь → статус **404** и содержимое `/404.html` (файл лежит в корне). Если в панели есть переключатель SPA/fallback на `index.html` — выключить.

### 3. Редиректы

Английские страницы переехали с `/en/<страница>/` на `/<страница>/en/`. Нужны 301:

```
/en/articles/            → /articles/en/
/en/articles/<slug>/     → /articles/<slug>/en/      (slug: a-z, 0-9, дефис)
/en/glossary/            → /glossary/en/
```

Варианты, в порядке предпочтения:
- включить поддержку `.htaccess` (`mod_alias`, `mod_rewrite`, `mod_headers`) — тогда всё из пунктов 1–3 уже настроено в нашем файле и больше ничего делать не нужно;
- или завести эти правила в панели (раздел редиректов), если он есть;
- или сказать, где на этой платформе задаются правила сервера, и дать к этому доступ.

### Если проще дать доступ

Мне хватит доступа в hPanel **только к этому сайту**: настройки кэша/CDN, редиректы, страницы ошибок (и, если есть, переключатель SPA-fallback / поддержки `.htaccess`). Доступ к другим сайтам, биллингу и DNS не нужен.

## Как проверить после изменений

```sh
# 1. кэш HTML: ожидаем max-age=0 (или короткий), а не 31536000
curl -sI https://jp-blog.travelpayouts.com/articles/market-size/ | grep -i cache-control
# ассеты могут остаться на год
curl -sI "https://jp-blog.travelpayouts.com$(curl -s https://jp-blog.travelpayouts.com/ | grep -oE '/_astro/[^"]+\.css' | head -1)" | grep -i cache-control

# 2. 404: ожидаем 404, а не 200
curl -s -o /dev/null -w "%{http_code}\n" https://jp-blog.travelpayouts.com/no-such-page-xyz/

# 3. редиректы: ожидаем 301 и новый адрес
curl -s -o /dev/null -w "%{http_code} → %{redirect_url}\n" https://jp-blog.travelpayouts.com/en/articles/market-size/
```

## Заодно, на будущее (не срочно)

Для стадии 2 (админка на Laravel, `docs/spec.md` §2.2, §11.1) понадобится: PHP **8.3+** с `mbstring`, `intl`, `pdo_mysql`, `curl`; MySQL; cron раз в минуту (`php artisan schedule:run`); отдельный поддомен для админки с document root на `laravel/public`. Стоит заранее проверить, поддерживает ли эта платформа такой вариант.
